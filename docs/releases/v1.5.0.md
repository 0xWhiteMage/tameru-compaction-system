# Tameru v1.5.0 — Hardened for serving, faster per tool result

Tameru v1.5.0 is the result of a red-team pass for hosts that compact untrusted tool output. It removes quadratic-time paths, widens the credential screen that gates recovery persistence, makes the per-result path about 4.6x faster and keeps the diff and grep adapters in charge when the question is asked in plain words. Compaction results on the comparison corpus, the 15-case QA battery and the budget sweep are unchanged.

## Highlights

- **Serving hardening.** Three inputs that could take tens of seconds now take milliseconds, with the same matches and outputs. A lone surrogate in the query or context no longer raises `UnicodeEncodeError`. The receipt no longer duplicates the input: `receipt["industrial"]["format_result"]` carries `text_chars` and `text_sha256` instead of the adapter's whole text.
- **Secrets screen: 70 of 80 sample credential shapes** (29 before). `contains_secret` recognises 41 more shapes, including AWS temporary keys, Google OAuth and refresh tokens, Slack, Stripe test and webhook secrets, Hugging Face, npm, PyPI, SendGrid, GitLab, Docker, DigitalOcean, Shopify, Square, Twilio, Mailgun and Telegram tokens, Azure account keys and SAS signatures, `scheme://user:password@host` URLs, Basic credentials, `sshpass -p`, `curl -u` and quoted-key JSON/YAML assignments. Placeholders and code stay unflagged; across 12,535 source, doc and config files 18 more files (0.14%) are flagged. The screen gates recovery-cache writes; it does not redact returned text.
- **About 4.6x faster per tool result.** Same-text analyses (preprocessing, segmentation and scoring, the secrets screen, error fingerprints, the input profile, token estimates) are remembered for texts of 2 KB to 1,000,000 characters, so a retry with another budget no longer re-analyses the output. Per-line regexes that cannot match are skipped. Outputs are unchanged.
- **Weak-query diffs and grep.** A unified diff asked about in plain words (“where was frobnicate changed?”) keeps whole hunks, every file header, per-file stats and `@@` lines instead of being cut inside hunks. Plain-word questions over an all-matching `rg` result use the saturated-query mode, so the definition line survives. Empty and filler-only queries still license no cut.

## Fixes

- Removed quadratic time on blank-line runs (`detect_format` SQL/INI and the code/SQL veto), on long single-word queries (`LATIN_IDENT_RE`) and on many-term queries (`score_blocks` recompiled each term's pattern for every block).
- Hash sites encode with `surrogatepass`, as `_sha256_text` already did.
- Memoization is bounded to texts of 2 KB to 1,000,000 characters, so a long-lived server never pins copies of multi-MB inputs.
- The test suite runs on Python 3.10 again (`tomllib` is 3.11+).
- Test-runner reduction (pytest, Jest, Go, Cargo) was checked and never depended on query specificity: no change.

## Performance

Engine CPU, cold caches, best of 3, on the release runner (from the CHANGELOG profile):

| Input | Before | After |
|---|---:|---:|
| 650 KB log, one tool result's row sequence | 4.05 s | 0.61 s |
| 50 KB log | 443 ms | 66 ms |
| 47 KB JSON dump | 343 ms | 64 ms |
| 25 KB grep output | 294 ms | 67 ms |
| 10 KB numbered source | 91 ms | 22 ms |
| Sum of the five | 5.2 s | 0.83 s |

A 13-tool-row prune pass through the Hermes plugin's engine fell from 0.92-1.07 s to 0.19-0.21 s with byte-identical rendered rows.

Re-measured for these notes (Python 3.14.0rc2, a different and slower machine; v1.4.1 source from commit `4964f14` against v1.5.0 `933aa33`):

| Check | v1.4.1 | v1.5.0 |
|---|---:|---:|
| `compress_context("\n" * 20000, ...)` | 19.5 s | 0.022 s |
| 20 KB single-word query | 73.3 s | 0.11 s |
| Adaptive call plus three fixed-budget retries, 64 KB log with error bursts | 436 ms | 52 ms |
| First call on each of the 16 comparison cases, total | 340-502 ms | 148-214 ms |

The first-call totals are the range of three runs. The comparison harness times repeated calls on identical text, which v1.5.0's memoization serves from cache, so its 12.83 ms recorded median is not restated for v1.5.0 (see below).

## Verification

Measured on this release (`933aa33`), Python 3.14.0rc2:

- **Tests:** 1,319 passed, 3 skipped (`python -m pytest -q`); 1,259 passed, 3 skipped with `-m 'not perf'`; the 60 `perf` tests pass. `ruff check .` is clean.
- **Release QA battery:** 15/15 passed, with the same savings as v1.4.1 (for example lexical distractor 96.7%, multi-hop 95.0%, large synthetic document 99.5%). The large synthetic document completed in 100.4 ms CPU time against a 1,200 ms gate (822.9 ms in the v1.4.1 record); `benchmarks/production-qa-v3-results.json` carries this release's timings.
- **Budget sweep:** 15/15 clean at every ratio; mean character savings 77.3%, 68.4%, 61.2%, 41.5% and 24.9% at ratios 0.1, 0.2, 0.3, 0.5 and 0.7.
- **Comparison corpus:** `python benchmarks/compare.py --verify-against benchmarks/comparison-v1.4.1.json` re-runs Tameru's arm on the recorded 16-case corpus. The corpus hash matches, and every output hash, saving (81.9% mean), retention result (25/25 required strings, 0 forbidden leaks, 16/16 clean cases) and determinism flag is identical to the v1.4.1 record. Timings are excluded from the check.
- **Packaging:** the wheel builds as `tameru_compaction_system-1.5.0`, and the installed wheel's `tameru-compress` CLI and `tameru.__version__` (1.5.0) pass a smoke check.
- **Behaviour-preservation evidence from the CHANGELOG (not re-run here):** 11,259 differential checks hash-identical between old and new engine under `PYTHONHASHSEED` 0 and 5; the recorded results of 3,135 engine API calls made by 854 tests are identical.

## Comparison record

The competitor comparison (LCC mechanical, Headroom TextCrusher, TF-IDF, LCC → Laya) was recorded on 2026-10-12 against Tameru v1.4.1 and was not re-run: the competitors need optional packages and models, and no number is carried under a new label. Tameru's v1.5.0 outputs equal that record's, so its scores stand. See [current comparisons](https://github.com/0xWhiteMage/tameru-compaction-system/blob/main/benchmarks/COMPARISON.md).

```bash
python -m pip install "git+https://github.com/0xWhiteMage/tameru-compaction-system.git@933aa33f6456c16db1b623e26ecc73c9b9be95d7"
```

Python 3.10+; no runtime dependencies or LLM calls for default extraction. Hermes users must update their separate plugin/vendor copy to receive the engine changes.

## Upgrade notes

- Receipts: code that read `receipt["industrial"]["format_result"]["text"]` should use `text_chars` and `text_sha256`, or the output text itself.
- Diffs and grep results queried with plain words now take the adapter path, so their output can differ from v1.4.1 (whole hunks, kept headers). Other inputs are unchanged.

See the repository [README](https://github.com/0xWhiteMage/tameru-compaction-system/blob/main/README.md) and [CHANGELOG](https://github.com/0xWhiteMage/tameru-compaction-system/blob/main/CHANGELOG.md) for usage, recovery requirements and known limitations.
